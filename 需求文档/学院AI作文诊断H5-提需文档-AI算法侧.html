一、一句话说清要什么

学生上传作文题目图 + 作文正文图，再带上他填的年级、学科、作文水平自评。请算法侧做两件事：

  1. 生成诊断报告——把图片转成文字，读懂这篇作文，产出一份包含「称号 + 能力维度数据 + 文字性点评」的报告。
  2. 生成推荐内容——拿诊断结果去判断缺哪个知识点，从已有课程与试题库里挑出对应知识点的课程和试题。

报告要能被前端直接渲染成图表和卡片，不需要前端再加工；推荐要能直接落到具体的课程和练习上。

二、背景与目标

直播间首次到访的初高中学生，听完一段作文讲解后，手上往往正放着一篇刚写完的作文。他们知道「要多练」，但不知道手上这一篇具体差在哪、下一步该练什么。本需求就是要在一次轻量体验里把这个问题回答掉。

对算法侧而言，本需求是整条链路的成败点：前端页面已经定型，用户在点下「开始 AI 诊断」之后到看到报告之间的全部体验，都由算法侧的两个能力决定。识别不准或报告空泛，前端做得再好也留不住人。

需要算法侧特别理解的两点 ① 输出即界面。报告的文字会原样呈现在学生和家长眼前，因此不只是「准确」的问题，还要「能读、不伤人、不像机器」——文案口径约束见 4.4。
② 这是手写体。作文纸是学生手写后拍照上传，不是印刷体扫描，识别难度显著高于常规 OCR，这是本需求最大的技术风险，见 4.6。

三、需求总览：两个能力

编号能力算法侧要做的事优先级

C2课程与试题推荐 基于诊断结果判断缺失知识点 → 从带标签的课程/试题库中匹配并返回推荐项 P0

四、能力一：作文诊断报告生成（C1）

4.1 输入

算法侧会收到以下信息，具体对接方式以平台侧为准，此处明确的是必须齐备的信息：

信息必传说明
学科是语文 / 英语。本期两个学科都要支持，且维度体系、评分口径分学科。
年级是用户在「写作情况」页选择（对应「高几」）。用于选评分基准与难度档位。
作文水平自评是用户主观填写的档位。仅作参考信号，不得直接决定分数，见 4.4 第 1 条。
期望提升方向否选填。可作为点评与推荐的加权偏好，缺失时按诊断结果自行决定。
作文题目图是题干 / 材料 / 写作要求，1 张。
作文正文图是含标题与全文。支持多页，需算法侧自行做多页拼接与顺序判定。

约束（与 PRD 一致）：支持 JPG / PNG；单张大小上限待确认；不做静默转码，其他格式不予受理。

4.2 算法侧需自行完成的处理链路

以下几点请算法侧内部闭环，不要回抛给前端或用户：

  1. 手写图文转写。把两类图片转成文本，输出「题目文本」与「正文文本」。
  2. 句子切分与编号。正文需切分成可引用的句子单元并带稳定编号——报告的「优秀句子」与「修改示例」要能指回具体句子。
  3. 多页顺序判定。正文多页时由算法侧判断页序，不要求用户手动排序。
  4. 题目与正文是否对应。PRD 已明确「题目与正文是否对应由诊断环节判断」。若正文明显跑题或与题目无关，需在报告中体现，而不是当作识别失败。
  5. 材料质量判定。图片模糊、反光、倾斜、文字过少、非作文内容（例如拍到无关画面）时，返回可解释的失败原因，供前端引导重拍。

4.3 报告需要包含什么

报告固定三部分，请按下面这份清单产出内容——每一部分都是学生和家长会直接读到的：

部分必须包含说明
第一部分
称号		 称号名、一句总结文案、状态标签 渲染在报告顶部的称号卡。三项都要给，缺任一项这张卡就不完整。
第二部分
能力维度数据		 每个能力维度给出：
1、维度名称
2、本维度的程度数值
3、本维度的定性档位
4、支撑该判断的原文依据 		程度数值供前端画图，定性档位供只展示文案时兜底，两者都要给（原因见 4.4 第 2 条）。
原文依据是让这个程度站得住脚的东西，不能凭感觉给。
第三部分
文字性点评		 1、写得好的地方
2、写得不好的地方
3、优秀句子（需指回原文）
4、修改示例（原文节选 + 改写示范）
5、本次优先提升项（含问题证据与一条可执行建议） 		「优秀句子」与「修改示例」必须能对应回识别出的原文句子，前端要据此做高亮标注。
另需一并返回 ① 识别出的原文文本（题目 + 正文），报告里的所有引用都从这里来；
② 本次诊断是否可信的判断——置信不足时前端不做强结论展示，改为提示样本不足、建议重新提交。

4.4 内容与口径约束（重要，请严格对齐）

这些约束来自已定稿的 PRD，属于验收项，不只是建议：

#约束说明
1自评水平不得直接决定分数 用户自评是主观信号。它只能用于调整表达方式与推荐偏好，不能拿来当评分基准——否则同一篇作文换个自评档位就换了分数，家长一对比就会发现。
2程度数值与定性档位必须同时给出 PRD 现行口径是只向用户展示程度环、不出现数字分数；而本次提需要求给出数值以便前端做图表。
因此请两个都出：数值供前端使用，定性档位供展示兜底。这一处口径冲突需要产品、教研、算法三方一起定，见待确认 4。
3优先提升项有且只有一个 由诊断维度与作文证据综合决定，不能简单等同于最低分维度。学生一次只能改一件事。
4修改示例的原文必须来自本次识别文本 不得改写、编造或引用范文。引用不完整时以省略号标识。
5改写示例只示范方向 不覆盖学生原文，也不宣称是唯一正确答案。
6不对学生作人格或能力定性 称号、总结与状态标签须积极、具体。禁止「你语言能力差」「没有写作天赋」这类表达；要说「这篇作文的论证还可以更有层次」。
7不承诺结果 不使用「看完必提分」「保证提升 X 分」这类话术。
8引用原文须一致 「优秀句子」与「修改示例」引用的文本，必须与识别出的原文句子逐字一致，否则前端高亮会对不上。
⚠ 需要三方一起定的一处口径冲突：能力维度是否向用户展示数字分数？ 已定稿的 PRD 写的是「四项能力维度只展示程度环，不向用户呈现数字分数」；而本次提需因为前端要用数据画图，要求算法侧给出每个维度的数值。
两种读法都成立：① 数值仅供内部与图表使用，界面上不出现具体数字；② 界面直接展示分数。
算法侧先按第 ① 种准备不会白做——程度数值与定性档位都出即可覆盖两种读法。请评审时给出结论，见待确认 4。

4.5 能力维度体系：语文与英语分学科

这是本次提需最需要教研侧先拍板的一件事。请算法侧不要把维度写死，按「学科 → 维度清单」配置驱动，否则加学科就要改链路。

学科能力维度状态
语文 审题立意 / 结构论证 / 语言表达 / 素材运用 已定四维固定（来自 PRD）
英语 待教研侧给定。（英语作文的评分关注点与语文差异明显，通常需覆盖内容完成度、语法准确性、词汇与句式、篇章结构等方向，且需处理拼写与语法错误的具体定位。） 待教研给见待确认 1
给算法侧的设计建议 建议把「维度清单、各维度评分标准、档位阈值」做成配置而非写死在链路里，由教研输出、算法消费。这样语文四维上线后，英语维度一到就能直接接。

4.6 失败与异常处理（对应 C4）

失败必须可解释、可指导，不能只给一个笼统的「诊断失败」。请按下面的场景分别返回可读的原因说明，前端会据此展示对应的引导话术：

场景需要返回什么前端会怎么做
图片模糊 / 反光 / 看不清说明是照片质量问题、看不清内容提示重拍，保留已选材料
正文文字过少说明正文内容太少，不足以做出判断提示拍完整篇
拍的明显不是作文说明材料内容不是作文提示重新确认材料
正文与题目不相关建议不作为失败处理，改为在报告中指出审题问题正常出报告，报告里体现跑题
正文多页拼接失败说明页序或页面衔接没能识别成功提示重新上传或分次拍摄
内部异常说明本次诊断未能完成提示稍后重试，保留材料

五、能力二：课程与试题推荐（C2）

5.1 要解决什么

报告告诉学生「你哪里不行」，推荐要告诉他「那我该看什么、练什么」。逻辑是：

诊断结果 → 判断缺哪个知识点 → 从库里挑出该知识点对应的课程与试题。

5.2 输入

信息说明
年级、学科推荐必须限定在同学科、同年级（或适配年级区间）的范围内，不能给高三学生推初三的课。
文体如议论文 / 记叙文 / 应用文。类型要匹配——「把议论文观点讲透」的课不能推给写记叙文的学生。
各维度评分结果能力一产出的能力维度数据。
优先提升项这是推荐的主锚点——PRD 要求推荐内容与优先提升项一致。
课程库 / 试题库带标签的存量资产；标签体系本身需教研侧先给，见第六章。

5.3 推荐需要输出什么

内容必须包含
知识点缺口 判定缺了哪几个知识点；每个知识点要说明为什么判定为缺，并关联回它对应哪个能力维度。
推荐课程 课程名、卡片上的类型文案、封面、时长，以及能唯一定位这门课的标识（前端要能跳转）；同时标明它匹配的是哪个知识点。
推荐试题 / 练习 练习名称、卡片上的类型文案，以及能唯一定位这组练习的标识；同样标明匹配的是哪个知识点。
是否走的兜底 没有匹配内容时会给兜底推荐，这种情况需要明确标识出来，前端和后续数据分析要能区分。

5.4 约束

  1. 与优先提升项一致。推荐内容须与本次优先提升项、作文类型、年级三者一致。
  2. 必须能唯一定位，不能只给文案。前端要能跳转——返回课程名却给不出课程编号，等于不可用。
  3. 课程下架或试题无匹配要有兜底。不展示失效入口，改推通用提升建议或兜底内容，并明确标识这是兜底结果。
  4. 不重复推荐。同一学生在同一会话内重复诊断，应避免反复推同一条让人产生「没听懂我」的感觉；去重策略请一并给出。
  5. 推荐项数量本期固定。报告页只呈现1 门课程 + 1 组配套练习，不要返回长列表。

5.5 与能力一的调用关系

建议：一次提交、一次返回 报告页需要同时渲染「诊断结果」和「推荐内容」，学生只点了一次「开始 AI 诊断」。
因此建议算法侧提供联合结果——一次请求同时返回能力一与能力二的内容；若拆成两个接口，请由平台侧在一次等待内完成串行编排，不要让用户为两次调用等两次。
这一点需要产品和算法一起确认，见待确认 5。

六、上游依赖（需教研侧先给）

以下三项不解决，能力一的能力维度部分与能力二整条链路都无法开工。产品会同步向语文、英语教研组提需：

#依赖项为什么是前置
1英语能力维度体系与评分标准语文四维已定，英语维度未定。维度不齐，能力维度数据就无法产出。
2各维度档位阈值与定性文案什么水平算「较突出」、什么算「待提升」，以及每个档位给学生看的话术。
3课程 / 试题的知识点标签体系能力二的匹配依赖标签。需要明确：标签粒度、一门课/一道题能否多标签、标签与年级学科文体的关系、标签库在哪里维护。

七、验收标准

以下为验收时会实际抽查的项，请按此准备演示与说明：

  1. 语文、英语两个学科各能跑通一篇真实手写作文（现场提供或事先准备），产出结构完整的报告。
  2. 报告的三个部分齐备：称号（含总结与状态标签）、能力维度数据（含程度数值与定性档位）、文字点评（含写得好的、写得不好的、优秀句子、修改示例）。
  3. 「优秀句子」与「修改示例」引用的原文，与识别文本逐字一致，前端高亮能对上。
  4. 「优先提升项」有且只有一个，且不是简单地取最低分维度。
  5. 维度数据能把前端图表画出来（数值区间明确，缺失时的表现也要明确）。
  6. 推荐结果能定位到具体课程与练习，且与优先提升项、文体、年级一致。
  7. 至少三类失败场景能返回正确的可解释原因，前端引导话术可用。
  8. 全流程无违反 4.4 约束的文案。

八、交付物与优先顺序

优先级交付物内容
P0技术方案评估实现路径、模型选型、手写识别方案与风险判断。建议本次评审就要拿到。
P0输出内容确认版基于本文件 4.3 / 5.3 的清单，反馈可实现的范围与冲突点。
P0能力一可联调版本能产出结构完整的报告，供前端接入。
P1能力二可联调版本依赖知识点标签体系就位。
P1失败场景与话术清单4.6 的完整场景列表与建议话术。

九、待确认清单

以下问题会影响开发排期与产出形态，请在评审时逐条给出结论：

#问题影响
1 英语的能力维度是哪些？是否与语文共用一套？ 决定能力维度数据能不能产出、英语能否上线。倾向方案：分学科各一套维度，由配置驱动。——需教研侧给
2 维度数值的量纲与区间是什么？（0-100 分？百分位？等级换算值？） 前端图表、档位阈值、跨学科可比性都取决于此。
3 同一学生在同一会话内重复诊断，结果是否要稳定？ 影响是否要加结果缓存或一致性约束。若一次诊断换一个称号和分数，家长会立刻不信。
4 【口径冲突】能力维度是否向用户展示数字分数？
PRD 现写「只展示程度环，不向用户呈现数字分数」，本次提需要求给出数值用于前端图表。		 两种读法都成立：① 数值仅内部/图表使用，界面不出现数字；② 界面直接显示分数。
需要产品、教研、算法三方一起定。算法侧按第 ① 种准备（程度数值与定性档位都出）不会白做。
5 能力一与能力二是联合返回还是两个接口？ 决定前端等待次数与报告页渲染时序。
6 单张图片大小上限与正文页数上限 PRD 中仍为「待确认」，会直接影响识别耗时与失败率。
7 知识点标签体系的维护方与更新频率 标签更新后推荐是否需要同步、由谁触发。
8 算法完全不可用时的降级形态 是整页不可用，还是降级为「仅称号 + 通用建议」。
